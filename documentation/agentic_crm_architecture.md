# Agentic CRM — Architecture

Status: approved direction (Prof. Shasha, Sept 26). Supersedes `chat_onboarding_architecture.md`.

## Goal

A small-business owner signs up, describes their business in a chat, and gets a working CRM on their own account. Later they change it the same way: add, modify, or remove features by chatting. No agency, no admin screens, no code.

## What we claim, and how it's measured

| Axis | Measured as |
|---|---|
| Flexibility | Share of requested changes the system can handle; works for industries with and without a template |
| Lightweightness | Turns and time from "I run a gym" to a working CRM; cost per change |
| Ease | A non-technical person can complete each task; number of corrections the agent needs |
| Quality | Zero code changed per business change (code leak); bad changes blocked and existing data preserved (change impact) |

Benchmarks: Baserow + Kuma (open-source AI builder, white-box), Airtable Omni (commercial reference), EspoCRM (non-AI baseline).

## Hard rules

1. **The agent never writes code.** It only proposes changes to a business's spec. The engine and UI are generic and render any valid spec.
2. **Propose, validate, approve, apply.** Every change is validated and impact-checked on the server, shown to the owner, and applied only after approval.
3. **Nothing is destroyed.** Removing a field or entity type archives it. Data stays and can be restored.
4. **Every change is versioned.** Each applied change creates a new spec version with a full record of who asked, what the agent proposed, and what was approved.
5. **Existing code stays untouched.** `/ui`, `questionnaire/`, `pipeline/`, and `frontend/index.html` are not modified. `main.py` gets additive lines only. `/agent` (config_agent) stays local-only behind `CONFIG_AGENT_ENABLED`.
6. **Account isolation everywhere.** Every read and write is scoped to the logged-in account.

## Core concepts

```
Account ── owns ──► Business ── has ──► Spec (current version)
                                         │
                                         ├─ entity types (Member, Lead, Location...)
                                         │    └─ fields (key, label, type, options, required, archived)
                                         └─ links between entity types

Business ── has ──► Records (rows of each entity type)
Business ── has ──► Spec versions (history: ops applied, by whom, when)
```

## The spec

Stored as JSON in the database, one row per version.

```json
{
  "business": { "name": "Sunshine Fitness", "industry": "health_club" },
  "entities": [
    {
      "key": "crm_member",
      "label": "Member",
      "archived": false,
      "fields": [
        { "key": "f_7k2a", "label": "Full name", "type": "text", "required": true, "archived": false },
        { "key": "f_9x1c", "label": "Membership", "type": "select",
          "options": ["Basic", "Premium", "Family"], "required": false, "archived": false }
      ]
    }
  ],
  "links": [
    { "key": "l_3m8d", "label": "Home location", "from": "crm_member", "to": "crm_location",
      "cardinality": "many_to_one", "archived": false }
  ]
}
```

- **Field types (v1):** text, long_text, number, date, boolean, select, multiselect, email, phone.
- **Keys are permanent and generated by the server**, never by the LLM. Labels are what the owner sees and can change freely.
- **Entity keys must start with `crm_`** (keeps them from colliding with the legacy `contact` / `follow_up` attribute rows).

## Operations (what the agent can propose)

| Operation | Example request |
|---|---|
| `create_entity_type` | "I need to track members" |
| `update_entity_type` (label) | "Call leads 'prospects'" |
| `archive_entity_type` / `restore_entity_type` | "We don't need vendors anymore" |
| `add_field` | "Track referral source on leads" |
| `update_field` (label, options, required) | "Add 'Student' to membership types" |
| `change_field_type` | "Trial days should be a number" |
| `archive_field` / `restore_field` | "Remove fax" |
| `add_link` / `archive_link` | "Members belong to a location" |

Initial setup is the same mechanism: the agent proposes a list of `create_entity_type`, `add_field`, and `add_link` operations against an empty spec.

Out of scope for v1: changing records through chat (records are edited in the UI), automation, payments, scheduling, calculated fields.

## Validation and impact check

Run on the server for every proposal, before the owner sees it, and again on apply.

**Validation (reject if any fail):**
- Entity and field references exist; keys follow the rules
- No duplicate labels within an entity type; no duplicate entity labels
- Field type is supported; select/multiselect have non-empty options
- Links point to existing, non-archived entity types

**Impact check (shown to the owner):**
- Records affected by each operation ("212 members")
- `change_field_type`: how many existing values convert cleanly and which don't
- `update_field` removing a select option: how many records use that option
- Making a field required: how many existing records are missing it (required is enforced only on new and edited records)
- Archiving: how many records' values will be hidden (not deleted)

## Agent turn

```
POST /api/businesses/{id}/chat   { messages: [...full history] }
  1. Build context: current spec, industry template (if any), allowed operation types, field types
  2. One Anthropic call with a tool/JSON schema that constrains output to:
       { reply, operations: [...] }
  3. Validate + impact-check the operations
  4. Save as a pending proposal (base_version recorded); return reply + proposal + impact
POST /api/proposals/{id}/approve   -> re-validate against current version; apply; new spec version
POST /api/proposals/{id}/reject
POST /api/businesses/{id}/revert   { to_version } -> applies a new version equal to an older one
```

- A proposal is refused on approve if the spec changed since it was made.
- Operations that fail validation are dropped from the proposal and listed with the reason, so the owner sees what the agent tried and why it was refused.
- Model and API key come from env vars (`ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`). Add Anthropic as a provider behind the existing `call_llm` interface so the provider stays swappable.

## Industry templates

JSON files in `operations_nerd/agentic/templates/` (e.g. `health_club.json`, `real_estate.json`) in spec format. They are given to the agent as a starting point and context, not applied blindly. Any industry without a template still works; the agent builds from the conversation alone.

## Accounts

- Email + password. Passwords hashed with a slow hash (bcrypt or argon2). Session cookie, `HttpOnly`, `Secure` in production, `SameSite=Lax`.
- Signup can be gated by an invite code (`SIGNUP_INVITE_CODE`) so the deployed link isn't open to everyone.
- One account can own several businesses.

## Data model (additive)

```sql
accounts        (id, email UNIQUE, password_hash, created_at)
sessions        (id, account_id, token_hash, expires_at, created_at)
spec_versions   (id, business_id, version, spec_json, ops_json, source,      -- source: agent | revert | template
                 proposal_id, approved_by, created_at)
proposals       (id, business_id, base_version, messages_json, reply, ops_json, rejected_ops_json,
                 impact_json, status, model, input_tokens, output_tokens, latency_ms, created_at, decided_at)
```

- `businesses` gains a `current_version` column (additive, nullable). `owner_key` from Phase 1 holds the account id.
- Records reuse `entities` + `entity_attributes` from Phase 1. Attribute names are field **keys**, not labels.
- `proposals` + `spec_versions` together are the audit trail (who asked, what was proposed, what was approved, tokens, latency).

## UI (one page, `/app`)

- **Login / signup** screen.
- **Left:** the business's CRM. Tabs per entity type; list view; create/edit form generated from the spec; archived fields hidden.
- **Right:** chat. Under each agent reply, a **proposed changes** card: each operation in plain words, the impact check, rejected operations with reasons, and Approve / Reject.
- **History** view: spec versions with "revert to this version".
- Safe DOM building, no `innerHTML`. Function over polish.

## Deployment

- Single service (Railway or Render) with a **persistent volume** for the SQLite file. WAL mode is already on.
- Env vars: `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `SIGNUP_INVITE_CODE`, `SESSION_SECRET`.
- Set a monthly spend limit on the API key in the provider console.
- `CONFIG_AGENT_ENABLED` stays unset in production.
- Back up the SQLite file before each deploy.

## Build phases

| Phase | Scope | Done when |
|---|---|---|
| A | Accounts, spec model, versions, validator, templates | Can sign up, create a business from a template, see version 1; tests pass |
| B | Operations engine: apply ops, impact check, archive/restore, revert | Every operation tested, including impact numbers and revert |
| C | Agent turn: proposal, approve, reject, audit fields | Stubbed-LLM tests pass; one live run creates a gym CRM |
| D | `/app` UI: CRM views from spec, chat, proposal card, history | Full flow in a browser: sign up, chat, approve, add records, change, revert |
| E | Deploy | Shareable link with invite-gated signup |
| F | Benchmark task suite | Same tasks run on ours and Baserow + Kuma, results logged |

## Benchmark task suite (Phase F)

Each run several times per system, recording success, turns, corrections, time, and cost:

1. Create a CRM for a business with a template (health club)
2. Create a CRM for a business without one (dog groomer)
3. Add a field to an entity type
4. Change a field's type with existing data
5. Remove a field, then restore it
6. Add a link between two entity types
7. A bad request (duplicate entity, unsupported type) — must be refused without damage
