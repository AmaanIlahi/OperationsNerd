# Food distributor: predictions

Written 2026-10-23, before any experiment. Revised the same day after a read of the code on main and on jasmeet/logistics-stock, still before any experiment.

Question: can a second goods business run on OperationsNerd with data shape by chat config only, rules in module code written once, and zero code per company?

Classes:
- pass: works today by chat config
- config gap: chat can't express it, but one core change fixes it for everyone
- module gap: needs LogisticsNerd module code, written once
- true break: needs code per company, or the owner has to write code
- silently wrong: works by config but produces incorrect results

Two businesses, same module: A, a produce distributor (kg, short shelf life); B, a frozen-goods distributor (cases, long shelf life).

## Data shape
| # | Requirement | Prediction | Why |
|---|---|---|---|
| D1 | Products: SKU, unit, storage temperature, shelf life days | pass | text, select and number fields exist |
| D2 | Suppliers and customers | pass | plain entities |
| D3 | Purchase orders with lines (line links to order and product, quantity, price) | pass | lines as their own entity with two many_to_one links |
| D4 | Sales orders with lines | pass | same shape as D3 |
| D5 | Lots: lot number, received date, expiry date, links to product and supplier | pass | date fields and many_to_one links exist |
| D6 | Lot number unique per product (scoped unique: lot number plus product link) | config gap | no unique option at all, and this needs uniqueness across a field and a link together, checked in app code the way one_to_one is today. A plain `unique` flag on one field would not fix it |
| D7 | Every order line must have a product | config gap | links can't be required |
| D8a | Exact money and kg amounts | config gap | number is a float, no decimal type. Floats survive storage unchanged; the loss appears once something adds or converts them |
| D8b | Decimal comma in quantities ("1,5" kg) | observed during review, not predicted | values.py treats commas as thousands separators, so "1,5" is stored as 15 with no error. Checked with coerce_value in the venv |
| D9 | Lot quantity entered as a config field | silently wrong | an editable number that bypasses the ledger and drifts from on hand as soon as anything ships; config should never hold stock |
| D10 | Sales line records which lots it shipped from | module gap | config could declare a many_to_one from line to lot, but FEFO can split one line across several lots, so that link would be silently wrong for split lines. The real record is allocation rows (sales line, lot, quantity) written by the module |
| D11 | One purchase order line received as several lots | pass for the shape; module gap for the stock | a many_to_one link from lot to purchase order line holds one line to many lots. receive() has no lot, and its source_ref is free text |

## Derived values and rules on records
| # | Requirement | Prediction | Why |
|---|---|---|---|
| R1 | Line total (quantity x price) and order total (sum of lines) | config gap | the core has no computed or summed fields |
| R2 | Expiry date after received date | config gap | the spec has no rule that compares two fields |
| R3 | Order status flow (draft, confirmed, shipped, ...) | pass for the field; module gap for the flow | a select field holds the status, but nothing enforces which status may follow which |

## Queries
| # | Requirement | Prediction | Why |
|---|---|---|---|
| Q1 | Lots expiring in the next 7 days | config gap | pass means the API answers it; a client paging through every lot and filtering itself does not count. The list endpoint takes only limit and offset. find_entity_ids_by_attribute is exact match only, so exposing it is not enough. A range filter would work on dates stored as JSON text, but not on numbers ("10" sorts before "9") |
| Q2 | Recall: which customers received lot X | module gap, plus D10 | nothing links a sales line to a lot today. The answer needs the allocation rows of D10 (sales line, lot, quantity), written by the module |

## Precondition
| # | Requirement | Prediction | Why |
|---|---|---|---|
| P1 | Field-role mapping: module code written once can find the config fields it needs (a product's unit, a lot's hold flag, a customer's minimum shelf life) | config gap | field keys are random per business (f_ plus 8 hex, regenerated by rekey_spec) and labels can be renamed, so module code has no stable way to name a field. One core change: the module declares roles, the owner binds fields to them by chat. M3b, M4, M5 and T1 depend on it |

## Rules
| # | Requirement | Prediction | Why |
|---|---|---|---|
| M1 | Stock tracked per lot | module gap | no lot on movements or reservations |
| M2 | Oldest expiry reserved first | module gap | reserve has no lot ordering |
| M3a | Expired lots can't be reserved or shipped | module gap | no expiry in the engine; the rule itself is the same for every company |
| M3b | Held lots can't be reserved or shipped | module gap, needs P1 | if the owner sets a hold through a config field, the module must find that field; same risk as M5 |
| M4 | Quantities in kg (A) and cases (B) | module gap, needs P1 and items from the core | store grams as integers, with a unit and scale per item. The engine is integer only, so B (cases, scale 1) fits it today; only A needs a scale |
| M5 | Customer-specific minimum shelf life ("at least 5 days left") | config gap (P1) plus module gap | the module reads the customer's setting through P1. A true break only if the form of the rule differs between companies, for example A wants "at least 5 days left" and B wants "at least 70% of shelf life left" |
| M6 | Catch weight: ordered in cases, invoiced by kg weighed per case | candidate true break | one line carries two units, and the weighed amount is only known at shipping. M4's single unit and scale per item can't hold it. Becomes a module gap if the module supports a second, measured quantity per line for every business |

## Two businesses, one module
| # | Requirement | Prediction |
|---|---|---|
| T1 | A and B both run on the same module, after M1 to M4 are built once, with no per-company code | pass, if P1 exists and units, shelf-life policy and FEFO are data, not code |

## Method
- Config changes go only through the real chat path: chat, then proposal, then approval. The stub provider always proposes nothing, so the model call in the chat module is replaced by scripted operation lists, as the existing tests do. The specs are never edited directly.
- Records go through the records API.
- A and B each get their own temporary database (DATABASE_PATH under a new temp directory), matching the decision that each company gets its own private database. The real database is never touched.
- LLM_PROVIDER=stub throughout. No live model is called.
- Module-gap rows are shown against the stock engine on jasmeet/logistics-stock as it stands. This experiment does not build module code.
- Each result is recorded next to its prediction. A wrong prediction is kept and marked wrong, not edited. Rows marked observed during review do not count as predictions.

## Not testable with a stubbed chat
- Whether a live model proposes one_to_many or many_to_many links for order lines, which can't hold values.
- Whether a live model adds a quantity field to Lot (the D9 trap) on its own.
These need a small live run, with explicit permission, later.
